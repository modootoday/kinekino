# 사용자 품질 검토 인수표

이 문서는 12시간 통합 목표의 사용자 시험 절차다. 현재 실행 성공이나 품질 승인을 기록하는 문서가 아니다. 실행 파일·표본·화면 경로는 통합 빌드 검증 뒤 확정하며, 확인하지 않은 경로와 버튼을 사용자에게 안내하지 않는다.

> **후속 소스·입장 정합성:** Catalog 최종 UI 후계 C445C58B...는 수동 poll/read/inspect/play 기술 단계 버튼5개만 제거한다. 카테고리·작품·회차 선택 뒤의 처리는 원 typed SDK/원 export의 자동 진행으로 연결되며, 그 버튼을 사용자 시험의 필수 조작으로 안내하지 않는다. 자동 진행의 실제 성공은 동일 합성 pin의 CLI/factory 회귀를 통과한 뒤 정상 GUI에서 확인한다. 빌드/증분은 D:/workspace/@myso-kr/com.kinekino.player/runtime/build-cache/native, TMP/TEMP는 D:/workspace/@myso-kr/com.kinekino.player/runtime/build-cache/tmp로 이전 중이다. 과거 C 경로의 실행 파일이나 기존294 producer 결과를 현재 검토 빌드로 안내하지 않고, SDK의 새 D normal binary provenance와 중앙 GUI 배정 뒤 실행 경로를 확정한다. 현재 수동 GUI·사용자 판정은 계속 미실시다.

> **소스 대조 주석 · r3 F0E9 / GUI 미확인:** 선택 소스의 제안 진입 선언은 `저장된 제안`의 `제안 목록 새로 조회` → `제안 문서 선택`·`제안 항목 선택` → `선택한 제안 열기`다(`player_shell/proposal_chooser.rs`의 원 라벨과 `viewing/proposal-chooser.tsx` forwarding). 실제9처럼 NeedsRepair/typed draft null이면 수동 수정 화면의 `직접 검토할 원문 항목 번호` 입력 → `선택한 원문으로 직접 수정하기` → 해당 수정 입력 → `수정본 저장` → `저장한 수정본 채택`을 서로 구별한다. 이는 선언된 경로·용어의 대조이며 클릭·route 수명·저장 성공을 확인한 사용자 안내가 아니다. 실제9에 개발자 편집·저장·판정을 쓰지 않는 기존 조건은 유지한다.

## 제공 전 개발 담당 확인

- 고정 실행 빌드의 커밋·해시·필수 런타임·실행 방법과 로컬 저장 위치를 함께 제공한다.
- 동일 SDK/CLI의 지원·오류·취소·저장 근거와 GUI 연결 근거를 구별한다.
- 표본마다 원본 출처·사용권·모델/revision/정밀도·실제 출력 여부를 표시한다. 수동 작성·합성·미검증 후보를 실제 모델 출력과 섞어 표시하지 않는다.
- 사용자 판정은 원본/후보 revision과 연결한다. 수정·저장과 채택·거절은 별도이며 재열기 후 판정 이력을 확인할 수 있어야 한다.
- 미지원·미연결 기능은 명시한다. 실패 시 원인과 보존된 입력을 보여 주며 성공 화면으로 덮지 않는다.

## 현재 실제 표본의 제한과 개발 인수 조건

원시 후보 판정 화면의 비동기 연결은 기존 단일 ExecutionHandle attachment와 Pending 소유자를 재사용한다. 선택이 A에서 B로 바뀌면 A의 늦은 응답을 B에 표시하지 않되, A의 원 terminal 수락·ACK·종료는 끝까지 처리해야 한다. ACK 실패를 새 판정 제출로 재시도하지 않는다. 이 연결은 coherent132의 typed controller·ACK·오류·복구·그래프를 포함한 지정 회귀19가 실제 테스트 실행 파일에서 통과했다. 해당 합성/구성 시험은 실제 제품 GUI 조작·실제 사용자 판정 저장소 인수 근거가 아니다. 실제 GUI 연결과 별도 검증 namespace의 정상 SDK 저장·재조회 근거를 통합 뒤 확인한다. 제품 profile의 Native 지원을 Web 지원으로 확대 표시하지 않는다.

실제 Gemma/Llama/Qwen 출력 9개는 원문 요청과 원시 후보를 보존한다. 현재 모두 typed draft가 없는 NeedsRepair 상태이며, 개발자가 자동으로 수리하거나 사용자 판정을 입력하지 않는다. 원시 후보의 품질 판정은 수정본 저장·채택 및 채택 출력의 품질 판정과 별개다. 후보를 수정하지 않고도 수정 필요·보류를 명시 기록하고 다시 조회할 수 있어야 한다.

현재 표본의 range는 모두 null이다. 요청에 선언된 cue 시간은 실제 영상 PTS와 검증된 구간이 아니므로 위 7번의 구간 재생·시간 정합성 인수를 충족하지 않는다. 실제 영상에 연결한 구간과 재생 근거를 추가하기 전에는 해당 항목을 미완료로 유지한다. 화자 분리·시간 정합성도 원문 요청만으로 지원 판정하지 않는다.

검토 입력 저장소의 초기 사용자 decisions는 0건이다. 개발자 CLI 기록·취소·이력 시험은 별도 검증 namespace에서 수행하며, 제공할 사용자 저장소를 시험 판정으로 채우지 않는다. 사용자에게 제공할 때에는 실제 지원하는 판정 용어와 화면 경로를 확정해 이 표에 대응시킨다.

실제 화면의 용어와 지원 작업은 최종 빌드에서 확인 후 안내한다. 위 구분을 UI에 연결하지 못했거나 원 ticket의 오류·취소·ACK 실패에서 영구 Busy로 남으면 개발 미완료다. 판정 실패는 새 요청으로 몰래 재제출하지 않고 원 입력과 이력 조회·재시도 가능 범위를 표시한다.
## 사용자 판정 기록

각 표본은 승인·수정 후 승인·거절·판정 보류를 구별한다. 사유와 대상 revision, 제품 빌드, 판정 시각을 연결한다. 개발 담당의 자동 검사 결과를 이 표의 사용자 판정으로 복사하지 않는다. 사용자는 품질을 판정하며, 조작 불능·저장 유실·표본 미연결은 개발 결함으로 처리한다.

> **확정 용어 차이 · 소스만 검토:** 위 `승인·수정 후 승인·거절`과 표5의 `채택 또는 거절`은 일반 인수 표현이며 실제9 원결과의 enum/버튼명이 아니다. r3 F0E9 선택 `raw_review_panel.rs`와 `manual-repair.tsx`의 원결과 값은 `usable`/`needs_changes`/`deferred`, 라벨은 `사용 가능 선택`/`수정 필요 선택`/`보류 선택`이다. 선택은 로컬 판정 선택이며, 메모와 별도의 `원결과 판정 기록`이 저장 동작이다. `needs_changes`를 일반적인 영구 거절로, `수정 후 승인`을 네 번째 raw verdict로 바꾸어 안내하지 않는다. `수정본 저장`·`저장한 수정본 채택`은 별도 동작이며 그 자체로 원결과 품질 판정을 기록하지 않는다. 채택 출력의 `사용 가능`/`수정 필요`/`보류`와 `명시적 판정 기록`도 원결과 이력과 분리한다.
>
> 선택 `studio/raw-review-panel.tsx`의 다시 열기 sibling은 원문·후보·기존 판정 이력을 읽는 화면으로 새 원결과 판정 기록 버튼을 노출하지 않는다. `같은 후보 판정 이력 읽기`를 새 판정·저장·채택 경로로 안내하지 않는다. 품질 판정 입력은 `manual-repair.tsx`의 `원 모델 결과의 품질 판정` 구역과 구별한다. 실제9의 NeedsRepair/typed null/range9 null, 하이라이트 영상 PTS 미연결 및 모든 GUI 사용자 시험 미실시는 그대로다. 소스 핀 `F0E9C56C00258FB0C1EC16DC13825A6DF17360DD81D4D6DAC0C9E6AE66D80E39`의 선언/producer 대조 결과이며 실제 버튼 동작·사용자 승인 근거가 아니다.

통합 후 실제 버튼·진입 경로와 알려진 결함을 이 절차에 반영하고 사용자에게 한 번에 제공한다. 전체 잔여 범위는 [12시간 통합 계획](user-review-build-12h-2026-10-25.md)과 [전체 게이트](full-product-integration-gates.md)에 유지한다.

## Native route 수명 수정 후 개발 재검증 순서

source267-r3의 실제 GUI는 Studio 내용을 표시했지만 AwaitingFrame/Slot(NotVideo)로 멈췄다. 따라서 사용자가 조작할 수 있는 검토 빌드가 아직 아니다. 후계의 실행 전 필수 조건은 SDK/UI 동일 RouteMediaPort 타입, 원 ticket과 scope/generation, 기존 callback 해제→native 퇴역 완료→Studio mount 순서다. 자동 시험에서 Pending/실패/취소/중복/외부·오래된 ticket과 첫 오류 보존을 확인한다. 실제 coordinator의 엔진→surface 정리와 새 lease 등록도 별도 확인한다.

그 뒤 정상 GUI 단독 슬롯에서 Viewing→실제 표본 Studio→Viewing→다른 표본 Studio 전환을 확인한다. 새 프레임의 실제 관측, 이전 child 정리, 입력 복귀와 정상 종료를 기록한다. 이전 frame 수치나 DOM mount만으로 Active 성공을 판정하지 않는다. 실제9 입력에는 개발자 판정·편집·저장을 쓰지 않으며, 저장 기능은 별도 SDK scratch namespace의 근거를 사용한다. 사용자의 실제 품질 판정은 검토 가능한 빌드 제공 이후에만 기록한다. 이는 새 시험 계획이며 아직 실행 결과가 아니다.
