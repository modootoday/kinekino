# 기능 패키지 추출 후속 계획

상태: 2026-10-19 **사용자 분리 승인·단계별 진행 중**. 최초 리서치 뒤 사용자가 권고 순서의 실제 추출을 승인했다. 실제 구현·검증은 각 담당 세션, 서브에이전트는 리서치만 맡는다. [조사 정본](../../sots/architecture/package-boundaries-research-2026-10-19.md)은 조사 당시 관측이며, 현재 구현은 [3개 패키지 검증 정본](../../sots/verification/application/package-extraction-2026-10-19.md)과 [현재 중앙 조율](../player/current-coordination.md)을 따른다. 기능 검증은 SDK/CLI, GUI 검토는 UI/UX·입력·API 연결 표시로 구분한다. 10/21 사용자 지시로 AI의 단계별 재개를 허용했고 실행별 배정은 [현재 배정](../player/execution-leases.md)을 따른다. 패키지 조사 자체가 추론 실행 권한은 아니다.

## 각 단계 필수 검증

1. 담당이 소유한 한 단계 source freeze 후 `cargo fmt --check`, `cargo test`, `cargo clippy --all-targets -- -D warnings`를 실행한다. 추출 crate뿐 아니라 루트 소비자와 Windows enabled adapter도 확인한다. 빌드 슬롯은 PM에 배정받고 새 cold compile을 여러 개 시작하지 않는다.
2. 명시 workspace members, path dependency, lockfile, `include_str!`/자산/SVG 상대경로, test fixture path와 Windows cfg를 확인한다. Meari submodule 및 별도 target/lockfile을 변경하지 않는다.
3. 기존 CLI 명령/schema/error/capability와 JSON fixture를 전후 대조한다. unsupported를 지원으로 변경하지 않는다. `ApplicationClient` typed 반환과 JSON execute의 의미가 일치해야 한다.
4. 기존 S1 저장과 신규 S2 source snapshot을 새 binary에서 읽고 CAS 충돌·불변 원문·receipt 재조회·잘못된 입력 fail-closed를 검증한다. 출력 변경이 필요하면 migration을 별도 결정하며 경로 이동과 섞지 않는다.
5. 기능 완료는 SDK/CLI의 실제 입력·출력·receipt로 판정한다. GUI에서는 이 결과의 표현·API 연결·입력·포커스·레이아웃만 점검하며 같은 변환·저장·CAS 기능 검사를 반복하지 않는다. UI 시각 완료에는 별도 시각 규칙의 확대/1:1/실행 증거가 필요하다. 패키지 이동만으로 UI 품질 완료 표시를 하지 않는다.
6. 실패 원문·명령·종료코드·source/bin SHA와 지원 범위를 책임별 verification 문서에 보존한다. 테스트·벤치마크는 Rust로 작성한다. 실제 OS 비 Windows 지원, 성능 개선, 모델 품질은 검증 전 주장하지 않는다.

## 이동·복구 정책

각 단계는 파일 이동과 import 변경, 최소 호환 facade만 포함한다. 기능 추가·저장 schema 변경·패키지 이름 변경을 같은 단계에 섞지 않는다. 실행 전 기존→새 경로 표를 만든다. 원본 source checkpoint와 Cargo.lock을 보존해 단계 단위로 복구하며 다른 세션의 작업을 reset/삭제하지 않는다. 후속 사용자 지시에 따라 검증된 맥락별 commit은 중앙 PM이 수행하며 push/저장소 공개는 실행하지 않는다.

## 2026-10-21 SDK 렌더 의존 조사 후속

현재 root feature의 실제 이름은 `native-proposal-window` 및 이를 포함하는 `native-observer-test-support`다. 문서의 Native 구성 별칭을 존재하지 않는 Cargo feature명으로 사용하지 않는다. `native_skip_cli` target은 Windows/common SDK/owned-process와 실제 CLI를 소비하며 직접 Meari renderer를 import하지 않는다. 반면 root의 presentation/eframe 의존은 무조건이고 Native feature는 실제 부모 권한 adapter와 renderer graph를 함께 활성화한다. 정적 조사이며 실행 의존 tree나 속도 개선 수치를 실측한 것은 아니다.

후속 순서는 다음과 같다. 현재 진행 중 원 gate를 중단/재시작하지 않는다.

1. SDK 담당이 실제 gate별 필요한 feature를 확인한다. standalone CLI 기능 검증은 default/no-renderer 구성 후보이고 typed parent/proof/child-first 인수는 원 enabled 구성으로 별도 유지한다.
2. 단계6에서 desktop consumer feature·presentation/GUI bin required-features·eframe/Meari 조립과 dependency를 같은 책임으로 분리한다. 기존 GUI 기본 실행 호환과 CLI 명시 no-default matrix를 모두 검증한다. WebView2/wry/windows는 CLI provider/pipe에도 필요하므로 일괄 제거하지 않는다.
3. 단계4의 실제 Meari WindowStamp/NativeParentClient/ScopedParent를 사용하는 parent adapter는 fake로 대체하지 않는다. standalone NativePlaybackHost/guard/result/SDK 정책과 renderer 조립을 구분한다.
4. 안정화된 application/domain과 필요한 adapter를 독립 SDK facade 패키지로 추출하고 호환 re-export를 제공한다. mpv 전체 선이동으로 순환을 만들거나 정책을 media-contracts에 몰아넣지 않는다. 현 단계는 조사이며 새 분리 구현 배정은 아니다.

최초 조사는 두 Markdown만 작성했고 당시 cargo 검사는 실행하지 않았다. 이후 부분 변경과 담당 인계는 [인계 기록](../../sots/architecture/package-extraction-owner-handoff-2026-10-19.md), 담당의 실제 검사는 위 검증 정본으로 구별한다. 현재 이 계획의 상태 표는 PM이 갱신하며 최초 조사 사실을 소급 변경하지 않는다. VM·DPI·새 장시간 시험·모델 다운로드·추론·사용자 앱 종료는 패키지 추출 작업에 포함하지 않는다.
