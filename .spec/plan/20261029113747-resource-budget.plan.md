# 호스트 반응성 우선 자원 예산

## 현재 호스트 우선 결정 — 2026-10-26

build-host은 D 없는 Samsung 980 PRO NVMe SSD/약63.34GiB RAM/32 logical CPU 환경이다. 사용자 지시에 따라 실제 C 프로젝트 runtime/build-cache를 사용한다. 제품 native, Meari meari-native, 실행기 resource-runner, 공통 tmp로 구분한다. 아래 D/HDD/C 공간 부족 수치는 원 호스트 역사이며 현재 호스트 제약으로 재사용하지 않는다. heavy1/jobs1/conservative2와 producer 독점은 유지하며 CPU 병렬도 최적화는 별도 실측 사항이다. 전역 설정 변경·새 다운로드 없음. [결정](../../adrs/player/adr-datalab-build-cache-2026-10-26.md), [검증](../../evidence/environment/datalab-cache-paths-20261026.md).

## 최신 사용자 변경: D 빌드 캐시 — 2026-10-25

C 용량 부족을 막기 위해 프로젝트 빌드 출력은 D의 `runtime/build-cache/native`로 통일한다. 아래 역사 항목의 C warm cache 우선 규칙은 이 결정으로 대체한다. 로컬 비공개 `.cargo/config.toml`의 build.target-dir/jobs1을 설정했고 cargo metadata --no-deps --offline으로 target_directory와 build_directory 모두 D임을 확인했다. 기존 runner의 환경변수/명시 target-dir도 SDK가 함께 전환하며, 이전 검증 소스·로그·필수 실행 파일의 custody 경로를 새로 발행한다. 전역 Rustup/Cargo 설정과 무관한 프로젝트는 변경하지 않는다. 기존 캐시 이전과 실제 후속 빌드의 D 저장 검증은 아직 미완료다. HDD I/O는 직렬 배정한다.

로컬 Cargo env의 TMP/TEMP도 runtime/build-cache/tmp로 강제하고 해당 D 디렉터리를 준비했다. C source mirror에서 실행하는 runner는 이 root 설정을 자동 소비한다고 가정하지 않고 별도 D 환경을 명시해야 한다. 최상위 AGENTS에도 D 통합 정책을 반영했다. 설정 파싱 및 Cargo metadata 확인 범위이며 컴파일러 자식의 실제 TEMP 관측과 D 빌드 성공은 후속 gate에서 검증한다.

실제 정리: 증분 캐시127,340파일/112,294,212,136논리B 삭제로 C free 차이99,412,389,888B, 과거 gate EXE/PDB173개/72,246,441,984논리B 삭제로 추가67,595,862,016B를 관측했다. 합계 실제 여유 차이167,008,251,904B(약155.54GiB)이며 다른 프로세스의 동시 쓰기에 따라 free는 소폭 변할 수 있다. receipt는 `.spec/evidence/environment/build-cache-{incremental,snapshot}-cleanup-2026-10-25.json`이다. 정확 사용자 Python 삭제 요청에 따른 일회 운영 코드만 사용했으며 새 Python 개발 도구는 저장하지 않았다. 최신 실행 파일·필수 원실패 재현 EXE·실제 표본/모델·원 소스/로그는 삭제 범위에서 제외했다. PowerShell 삭제 거부 및 Python metadata 시각 epoch 환산의 삭제 전 중단은 완료 실행과 구별해 보존한다.

2026-10-19 사용자 지연 보고에 따른 중앙 실행 규칙이다. 전체 제품 범위와 기존 검증 의무는 유지하며, 무거운 작업을 동시에 시작하거나 반복 실행해 호스트를 압박하지 않는다.

## 관측과 즉시 조치

지연 보고 시 cargo/rustc/플레이어 실행 프로세스는 없었다. 물리 메모리63.93GiB 중 약25GiB가 남았고 commit52%, pages/sec0, 디스크 대기열0이었다. 측정 순간 ChatGPT renderer PID25124는 CPU 한 코어 이상, InventorySvc의 단독 svchost PID21084는 CPU와 I/O를 사용했다. 이는 순간 관측이며 지연의 단일 원인을 확정한 것이 아니다.

모든 담당의 새 실행·브라우저·추론·반복 프로세스/스레드 조회를 보류했다. InventorySvc의 단독 프로세스임을 재확인한 뒤 PID21084 우선순위를 Normal에서 BelowNormal로 일시 변경했다. 서비스 종료·시작 유형 변경·ChatGPT/Terminal 종료·VM/DPI 변경은 하지 않았다. 이 우선순위 변경은 해당 프로세스 수명에 한정되며 시스템 시작 설정을 바꾸지 않는다. 복원 시에도 PID/서비스/프로세스 identity를 다시 확인해야 한다.

사용자는 조치 후 데스크탑이 '정상에 가까워짐'이라고 응답했다. 인과관계나 완전 복구를 단정하지 않는다.

## 현재 진행 정책 — 사용자 정정 반영

호전 피드백 직후 SDK만 재개하고 UI/Meari까지 대기시킨 중앙 지시는 자원 관리를 작업 중단으로 과하게 해석한 조치였다. 사용자의 계속 진행 지시로 이 제한을 대체한다. SDK·UI·Meari는 소유 경로에서 저자원 소스 구현을 병렬로 계속하며, 무거운 실행만 직렬 배정한다. goal 상태는 실제 get_goal 결과로 확인하고 스레드 idle과 혼동하지 않는다. 목표가 없으면 담당 전체 목표를 등록하며, 미완료 목표를 완료 처리해 교체하지 않는다.

## 다음 실행 조건

기존 `tools/validation/src/infrastructure/processes.rs::measure_in`은 BelowNormal과 추론 엔진별 thread4 환경변수만 설정하고 CPU affinity를 제한하지 않는다. 해당 일반 측정 경로를 그대로 빌드 제한기로 사용하지 않는다. 별도 Rust `tools/resource-runner`는 JobObject의 affinity/priority 설정·읽기 대조 뒤 소유 launcher를 할당하며, 실제 child affinity3/2 logical CPU/priority16384를 기록했다. 실행기 자체 fmt/test1/strictClippy/build와 후속 SDK·UI 소비자 적용이 확인됐다. 자원 제한 동작과 제품 기능 성공은 구별한다. [실행기 근거](../../sots/verification/application/resource-runner-2026-10-19.md), [SDK 실제 frame CLI](../../sots/verification/application/frame-document-cli-2026-10-19.md), [UI controller SDK gate](../../sots/verification/presentation/proposal-controller-2026-10-19.md)에 실패·수리·최종 원로그와 적용 범위를 둔다.

- 저자원 소스 구현·계약 조율·UI 연결은 병렬로 계속한다. 빌드·실제 실행의 자원 슬롯 대기를 담당 전체 작업 중단이나 goal 종료로 확대하지 않는다.
- 무거운 실행은 프로세스 계열 하나만 허용한다. 소유 작업용 launcher와 그 자식만 낮은 우선순위·최대 두 logical CPU로 제한하고 cargo -j1을 유지한다. 사용자 앱의 affinity/priority는 변경하지 않는다.
- affinity 제한 때문에 전체 캐시를 무효화하는 compiler flag나 전역 환경 설정을 추가하지 않는다. 측정 결과에는 실행 예산을 기록한다.
- 캐시를 사용하는 필요한 검사부터 진행하고, 변경 없는 checkpoint의 전체 검사를 반복하지 않는다. 필수 검증을 생략해 완료로 표시하지 않는다.
- 출력은 파일로 보존하고 사용자 화면에는 단계별 결과만 짧게 보고한다. 여러 세션의 동시 진행 메시지·짧은 wait·반복 CIM/스레드 조회·전수 파일 검색을 하지 않는다.
- 자원 측정은 새 무거운 단계 직전과 이상 징후가 있을 때만 수행한다. 메모리/디스크 여유가 있다는 이유만으로 UI 지연을 부정하지 않는다.
- 재차 지연이 발생하면 새 실행을 보류하고 실제 소유 프로세스와 사용자 앱을 구별한다. 시스템 서비스·사용자 앱의 종료나 보안 제외를 임의 적용하지 않는다.

2026-10-21 사용자지시로 AI 전체보류는 해제했다. [현재 하드웨어 기반 단계 재개](ai/resource-allocation-2026-10-21.md)에 따라 입력/CLI 연결은 병렬, 실추론·다운로드는 단일worker/중앙배정으로 진행한다. Pages·VM·DPI·새 장시간 시험의 보류는 유지한다. 아래 과거 AI보류 기록은 당시 이력이다.

## 빌드 문맥별 산출물 분리 — 2026-10-20

제품 parent 등록 검사에서 같은 shared target의 consumer가 Serde 타입 식별 오류를 냈으며, 전용 target에서는 해당 컴파일 오류 없이 시험에 도달했다. 동일 버전/checksum과 다른 Meari fingerprint가 해시 없는 libmeari.rlib를 참조한 관측이다. 일반 toolchain 결함이나 기존 캐시 손상을 확정한 것은 아니다. [실행 정본](../../sots/verification/application/sdk-product-parent-2026-10-20.md)에 첫 실패와 격리 결과를 보존한다.

현재 root는 `%USERPROFILE%/AppData/Local/CodexBuildCache/project-9dc296c4/native`, consumer는 `runtime/build-cache/sdk-product-parent-consumer`를 사용한다. 중앙 슬롯 배정 때 workspace·feature graph·crate-type의 빌드 문맥과 target을 함께 확인한다. Meari 자체 workspace 등 다른 문맥의 해시 없는 산출물이 root/consumer target을 덮지 않도록 구분한다. 단일 heavy 순차 실행만으로 산출물 문맥 분리가 보장되지는 않는다.

동일 문맥의 캐시는 계속 재사용하고 Cargo registry source cache는 공유한다. 기존 target 삭제·전역 캐시 정리·컴파일러 flag 변경·불필요 cold build를 실행하지 않는다. 새 전용 target이 필요한 경우 디스크 여유와 증가량을 해당 checkpoint 근거에 남긴다.

작성 중인 다른 소유자의 path dependency까지 `cargo fmt --all`로 순회·수정하지 않는다. SDK는 제품 workspace 7개 package의 `cargo fmt --check`를 기본으로 하고 필요하면 package를 명시한다. Meari의 미완성 모듈 선언 때문에 dependency 순회가 실패한 첫 원문은 보존하며, 이를 root 컴파일 실패로 집계하거나 외부 파일을 임의 수리하지 않는다. consumer가 Native crate를 실제로 소비하는 검사 전에는 해당 소유자에게 해석 가능한 checkpoint와 소스 동결을 요청한다.

### NTFS 압축 대안 — 지원 확인만

Get-Volume은 C NTFS/4096 allocation unit, 관측여유14,750,658,560B(약13.74GiB)를 보고했다. `C:/Windows/System32/compact.exe` 존재 및 `/?` 도움말에서 NTFS 파일압축 `/C`, 실행파일 최적화 `/EXE` 선택의 지원을 확인했다. 고정42개의 현재 Attributes는 Archive이며 Compressed0/ReparsePoint0이다. `fsutil fsinfo volumeinfo C:`는 Access denied여서 그명령의volume capability조회는 확보하지 못했다.
