# kinekino 미구현 기능 인벤토리와 단계별 구현 로드맵

## Goal

main `c68eece` 기준 남은 미구현·부분 구현 기능을 근거 있는 항목만 목록화하고, Rust 우선·CLI 우선·Windows 마지막 검증 원칙으로 단계(P0~P8)를 정한다. 현행 개발 목표는 Linux 베이스에서의 완전 동작이며, Windows 기능은 DATALAB에서 사용자 확인된 상태로 보고 모든 구현이 끝난 뒤 P8에서 재검증한다. 브라우저 엔진(`feat/browser-engines`, ADR 0002)과 마스코트 3D 모션 프리셋은 범위 밖이며 의존성으로만 표시한다. 판정은 코드·문서 대조이며 이번 작업에서 빌드·실행 검증은 하지 않았다.

근거 정본: [재설계](../../../kinekino-redesign.md) §7, refactor-log plan, gaps plan, completion-audit plan, cli-migration-gaps plan, remaining-executors-20261028 plan, cli-feature-evidence-ledger-20261028 plan, `crates/kinekino-player/src/application/api/capabilities.rs`.

각 crate는 Cargo 표준(`src/lib.rs`, `tests/`, 버전·lint는 `workspace = true` 상속)을 따른다.

### 진입점

- 단일 부트스트랩 경로: `main` → `kinekino_app::bootstrap(Args, Env) -> App` → CLI 또는 GUI 모드. CLI와 GUI가 같은 SDK·같은 composition root를 쓴다(AGENTS CLI 우선 규칙).
- composition root는 플랫폼 무관: `PlatformHost`(OS 탐지·capability 보고)만 받아 레지스트리에서 어댑터를 고른다. root 안에 `cfg(windows)` 없음.
- 설정 로드 순서 하나로 고정: 기본값 → 설정 파일 → `KINEKINO_*` env → CLI 인자. 비밀은 설정에 없음(OS 자격증명 저장소 포트).

### 인터페이스 규약

- capability 선언: 모든 어댑터 포트는 `kind()`와 `capabilities() -> CapabilitySet`을 갖고, 미선언 기능은 `Unsupported`를 돌려준다(browser 포트와 같은 형식).
- 오류: 포트별 오류 enum은 공통 `ErrorCode{Unsupported, Unavailable, InvalidInput, Cancelled, Timeout, Quota, Auth, Io, Internal}`과 `retryable` 여부로 매핑되어 SDK/CLI JSON 오류로 일관되게 나간다.
- 이벤트: 포트는 `drain_events()` 또는 Jobs 이벤트로 typed enum을 낸다. 콜백 대신 pull/채널.
- 설정: 포트별 `Config` 구조체(serde, 기본값 있음), 비밀 필드 금지.
- 스레드: 어댑터 인스턴스 소유는 하나의 owner, 공유가 필요하면 포트에 `Send` 요구를 명시.

### 팩토리·레지스트리

- `Registry<P>`: 어댑터 팩토리 등록 `register(kind, factory, declared: CapabilitySet, availability)` → `select(platform, required, policy) -> Selection` → `build(selection, config) -> Box<dyn P>`. 선택 결과와 거절 사유는 capabilities CLI에 노출.
- 대상: 플랫폼 어댑터, BrowserEngine, PlaybackBackend·VideoSurface, InferenceBackend(cloud/local_first/local_only 정책), MascotEventPort.
- 어댑터 crate가 자기 factory를 `cfg` 안에서 등록하고, composition root는 등록 목록만 소비한다.

### feat/browser-engines와의 일치·차이

- 일치: `BrowserEngine` 포트, `EngineKind`, `CapabilitySet` 선언표, `select(platform, required, availability)`의 default→fallback 순서, 계약 스위트(`engine::contract`). 이 형식을 전 포트 규약의 기준으로 삼는다.
- 차이 1: browser `select`는 `Selection{kind, role}`만 돌려주고 인스턴스 생성은 호출자 몫이다. 공통 `Registry::build`로 감싸 다른 포트와 맞춘다(browser 브랜치 코드 수정 불필요, 래퍼).
- 차이 2: `EngineError`는 자체 enum이다. 공통 `ErrorCode` 매핑만 추가한다.
- 차이 3: 포트와 어댑터가 kinekino-browser 한 crate에 있고 cfg도 그 crate 안에 있다. 경계 규칙상 허용(어댑터 crate 안 cfg)하되, 포트만 쓰는 소비자가 어댑터를 끌어오지 않도록 포트와 어댑터를 feature로 분리한다(2026-10-30 확정).
- 차이 4: `BrowserEngine`에 `Send` 요구가 없다. 단일 owner 규약과 일치하므로 유지.

### cfg(windows) 누수 제거 계획

- 현황: cfg(windows) 335곳, player infrastructure 74 모듈 중 60, player `main.rs` 전체. 목표: 어댑터 crate 밖 0(재설계 목표 ≤10을 강화).
- 순서: (1) P0에서 lint로 현 위치를 allowlist 고정, 신규 0. (2) 포트 추출 순서 platform fs/process → playback(mpv, surface) → browser provider → studio 어댑터 → GUI. (3) 모듈 이동마다 allowlist 감소를 P1 완료 기준으로.

### lint-structure 규칙 추가(P0 산출물)

- R-cfg: `cfg(windows|unix|target_os)`는 adapter crate(목록 고정)에만.
- R-dep: domain/application crate는 adapter crate에 의존 금지, bin crate는 composition crate만 의존.
- R-ver: crate Cargo.toml의 외부 의존 버전은 `workspace = true`만.
- R-entry: bin `main`은 composition 호출 외 로직 금지(줄 수 상한).
- R-port: 포트 trait는 contract 위치에만 정의.

### 계약 테스트(P0 산출물)

- 포트별 공통 계약 스위트 하네스(browser `engine::contract` 형식 일반화): capability 선언대로 동작, 미선언은 Unsupported, 오류 코드 매핑, 취소.
- 레지스트리 선택 테스트: 플랫폼×필수 capability×availability 표로 선택·거절 사유 고정.
- 부트스트랩 스모크: Linux에서 CLI가 composition root를 거쳐 capabilities를 보고(GUI 없이).

## 추론 백엔드 설계 (P1b)

결정(2026-10-30, 사용자): 추론은 모델 직접 다운로드 없이 Hugging Face 클라우드 API가 기본값, 로컬 모델은 사용자가 명시 설치했을 때만 쓰는 선택 경로. 이번 작업은 설계만이며 실제 HF 호출·과금은 하지 않았다. 계정은 cw4196.

### 포트

`InferenceBackend`(Rust trait, ai 컨텍스트 domain 포트). 태스크별 typed 요청/응답: `Transcribe`(오디오→text+chunks 타임스탬프), `Diarize`(오디오→화자 구간), `Ocr`(이미지→텍스트 영역), `SegmentSubject`(이미지→마스크), `Generate`(번역·요약 등 chat), `Embed`(색인). 응답 스키마는 어댑터와 무관하게 동일하며 `provenance{backend, model, provider, cost_estimate}`를 붙여 기존 ai_provenance에 기록한다. 모든 호출은 Jobs 경로(취소·재시도·재시작)로만 실행한다.

### 어댑터

- 기본 `HfCloudBackend`: HTTP(router.huggingface.co). chat 계열은 OpenAI 호환 `/v1/chat/completions`, 그 외 태스크는 provider별 태스크 API. 모델 id 뒤 `:fastest`/`:cheapest`/`:preferred` 또는 provider 이름 접미사로 라우팅한다(공식 문서). Inference Endpoints(전용 배포)는 HF Providers에 없는 태스크(화자분리)를 위한 선택 대상.
- 선택 `LocalBackend`: whisper.cpp, ONNX Runtime 등. `models install/remove`는 이 로컬 선택 팩의 설치·검증·삭제로 의미를 재정의한다(사용자 명시 명령만, 자동 다운로드 금지).
- 시험 `MockBackend`·목 HTTP 서버: 녹화한 응답 fixture로 HF 어댑터를 네트워크 없이 시험.

### 선택·폴백 정책

- 기본 `cloud`. 설정 `inference.mode = cloud | local_first | local_only`. `local_first`는 설치된 팩이 있으면 로컬, 없으면 클라우드. 오프라인(네트워크 없음/토큰 없음)이면 로컬 팩으로 폴백하고, 팩도 없으면 typed `Unavailable{reason}`으로 거절한다(조용한 실패 금지).
- 폴백·모드 전환은 결과 provenance에 남긴다.

### 지연·쿼터·재시도·타임아웃

- 태스크별 연결/전체 타임아웃, 429·5xx만 지수 백오프 재시도(상한 횟수), 4xx는 즉시 실패. 긴 오디오는 구간 분할 후 Jobs 단위 진행. 구체 수치는 측정 전 미확인이라 설정값으로 둔다.
- HF 쿼터·rate limit 수치: 미확인.

### 비용 가드

- 월 한도, 건당 상한, 한도 근접 시 사용자 확인. 호출 전 예상 비용을 계산할 수 없으면 사용자 확인을 요구한다. 로컬 원장에 호출별 비용 추정 기록.
- 공식 근거: pay-as-you-go, HF 마크업 없음, PRO 월 $2 크레딧(Inference Endpoints·Spaces·Jobs 공용), 무료 계정은 크레딧 구매 필요, hf-inference는 compute 시간×하드웨어 단가. 사용량은 설정 페이지에서 조회; 조직 사용량 API는 Enterprise 전용. 태스크별 단가: 미확인.

## MCP 서버 (P9, 항목 id `P9-mcp-server`, 2026-10-30 사용자 지시)

목적: kinekino는 사람이 GUI로, AI가 CLI 또는 MCP로 같은 기능을 쓰도록 설계한다(CLI를 만드는 이유). MCP는 CLI의 두 번째 표면일 뿐 별도 기능을 갖지 않는다. 홈페이지의 "MCP planned" 표기는 이 항목 id를 가리킨다.

### 설계

- 단일 원천: 도구 목록과 입력 JSON Schema는 `kinekino schema`가 내는 `GROUP ACTION` 스키마에서 생성한다. 도구 이름은 `group.action`, 설명·인자·오류 코드는 스키마 그대로다. capabilities에서 현재 OS·빌드가 미지원(`unsupported`)인 명령은 목록에서 빠지거나 `unsupported`로 표시된다. 손으로 쓴 도구 정의는 두지 않는다.
- 실행 경로: 도구 호출은 CLI와 같은 application `Request` → `ApplicationClient`(로컬 host는 `EndpointClient`, OS IPC 포트)로 간다. 응답·오류(`ApiError` code/retryable/details)는 MCP tool result로 그대로 직렬화한다. Jobs는 MCP progress 알림과 `notifications/cancelled`를 Jobs cancel에 연결한다.
- 전송: stdio 우선(MCP 2026-07-28 stdio 바인딩: stdout은 MCP 메시지만, 로그는 stderr, stdin EOF가 종료 신호). Streamable HTTP는 범위 밖이며 필요 시 별도 ADR.
- 라이브러리: 공식 Rust SDK `rmcp`(3.x, 2026-07-28 구현, `transport-io`). 어댑터 crate `kinekino-mcp`(composition은 kinekino-app)에 두고 core는 MCP를 모른다.
- OS 중립·권한: MCP 서버는 사용자 세션의 자식 프로세스로 돈다. 로컬 host 연결은 기존 `OsPolicy::ipc()`와 어댑터 `permits`(같은 principal, 권한 혼합 거부) 경로를 그대로 쓰며 MCP 전용 인증 경로를 만들지 않는다. 노출 허용은 `settings.mcp.allowed_tools`가 정한다.
- 토큰: stdio에는 토큰이 필요 없다(프로세스 소유자 = 사용자). HTTP 전송이 생길 때만 CredentialStore 포트의 토큰을 쓴다.

### 설정 페이지(`settings.mcp`, CLI `kinekino settings` 동일)

|키|타입·기본값|비고|
|---|---|---|
|`enabled`|bool, 기본 `false`|꺼져 있으면 `kinekino mcp serve`가 이유와 함께 종료|
|`allowed_tools`|`read_only`\|`standard`\|`all` 또는 `group.action` 목록, 기본 `read_only`|파괴적·과금 명령(삭제, 실 추론 호출)은 `all` 또는 명시 목록에서만|
|`confirm_destructive`|bool, 기본 `true`|MCP elicitation으로 사용자 확인, 미지원 클라이언트는 거부|
|`token`|등록/삭제/상태만(값 표시 없음)|CredentialStore, HTTP 전송 전용(현재 미사용)|
|`client_config`|표시 전용|Claude·Cursor 등 클라이언트에 붙일 stdio 실행 설정 스니펫 복사|

### 완료 기준

1. `kinekino mcp serve`(stdio)가 initialize/tools.list/tools.call을 처리하고, tools.list가 `kinekino schema`와 이름·스키마 일치(스냅샷 테스트로 드리프트 검출).
2. `allowed_tools` 밖의 도구는 목록에 없고 호출 시 거부, `enabled=false`면 기동 거부.
3. 오류·취소·progress가 CLI와 같은 코드로 전달.
4. Linux에서 실행 검증, Windows는 P8에서 재검증. 공통 기준(fmt, clippy, test, lint-structure 신규 0, spec-check 0 오류).

### 검증

- MCP 계약 테스트: `rmcp` 클라이언트(`transport-child-process`)로 실제 바이너리를 띄워 initialize→tools.list→tools.call(`version`, `capabilities`)→취소→stdin EOF 종료.
- 목 클라이언트: 인프로세스(`transport-worker`)로 허용 목록·확인 거부·오류 매핑 단위 테스트, 목 `ApplicationClient`로 host 없이 실행.
- 스키마 스냅샷: CLI 스키마와 MCP 도구 목록 비교.
