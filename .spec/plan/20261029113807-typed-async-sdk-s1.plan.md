# S1 typed async UI 경계

2026-10-20 PM 배정·SDK exact port 합의. SDK가 단일 heavy를 소유하며 UI는 source/시험 작성만 수행한다. cargo/GUI·모델·다운로드·DPI/VM 실행 0, 새 의존성/manifest/lock/Core/Native/SDK source 변경 0. 계약 합의와 실제 지원 완료를 구별한다.

## 책임과 파일

| 소유 | 파일·역할 |
|---|---|
| SDK | `src/application/sdk_execution/`의 plain canonical Request/Response·operation·terminal·ACK·cancel·close, bounded executor와 게시 의미. `src/assembly/meari/`의 5개 capability/typed DTO 주입·ticket↔operation 상관 연결 |
| UI generic plugin | 새 `packages/player-ui-plugins/src/infrastructure/typed_async_sdk_plugin/{mod.rs,codec.rs,lifecycle.rs,tests.rs}`. typed request/reply/ApiError 검증 및 실제 owner start/peek/ACK/cancel/shutdown 위임. 완성 checkpoint 이후에만 기존 `infrastructure/mod.rs` export 등록 |
| UI presentation | 새 `src/presentation/web_ui_adapter/proposals/{pending_host.rs,pending_controller.rs,pending_controller/tests.rs}`. 기존 `registry_host.rs`·`controller.rs`의 Immediate 경로는 보존한다. 기존 document_session/window_bridge/intent_queue의 연결 변경은 별도 배정/회귀가 필요하다 |

package는 root SDK를 import하지 않는다. assembly가 canonical DTO를 generic I/O type parameter로 주입하며 executor/store/취소·publication 정책은 SDK에 하나만 둔다. 실제 PluginTicket·registration·scope·view selection·PendingToken은 UI thread의 실제 owner ledger에 유지한다. worker에는 보내지 않으며 JSON/정수에서 재구성하지 않는다.

## 합의한 Rust 경계

정본은 [SDK execution 공유 계약](../../../sots/player/application/api/sdk-execution.md)이다. SDK application은 private owner+sequence의 OperationId 및 canonical Request/Response·ExecutionTerminal을 소유한다. UI generic AsyncSdkPort<I,O>는 mut start(actual ticket,I)→(), 비소비 peek_terminal(ticket)→Option<Arc<Result<O,ApiError>>>, acknowledge(ticket)→(), cancel(ticket)→CancelReceipt, shutdown()→()를 제공하며 오류는 PluginError다.

SDK assembly가 actual ticket↔OperationId와 canonical Response→typed Arc 캐시를 소유한다. package는 root 타입을 참조하지 않으며 actual ticket과 registry 수락 event/ACK 상태만 추적한다. Arc<Result>로 ApiError/O Clone을 강제하지 않는다. 별도 TypedAsyncSdkPlugin과 같은 상태를 공유하는 AsyncSdkPump를 registry 밖에서 호출한다.

- admission 실패는 Pending으로 포장하지 않는다. 수락하면 actual ticket으로 Pending을 반환하고 registry Pending 등록 후에만 결과를 수락한다. early completion은 owner에 보존한다.
- typed reply/error는 generic codec과 registry에서 검증하고 actual ticket의 `accept_event` 성공 뒤에만 owner ACK한다. ACK 실패는 accepted-but-unacked로 보존한다. registry에 같은 terminal을 다시 전달하거나 SDK mutation을 재실행하지 않는다. invalid typed terminal은 원 결과를 보존해 명시 오류/정리 재시도로 남긴다.
- queued 제거를 확인한 SDK도 provider에서는 Requested로 유지하고 canonical ApiError(code=Cancelled)를 Core Failed details로 수락한 뒤 ACK한다. in-flight 또는 terminal-ready도 Requested로 두고 실제 Completed/Failed를 전달한다. cancel이 terminal-ready 결과를 삭제하지 않는다.
- close는 새 admission을 차단하고 기존 terminal/ACK를 drain한 뒤 shutdown을 위임한다. Busy·borrow·ACK·join 실패에서 같은 owner/실제 ticket을 보존해 재시도한다. Drop/timeout을 정상 close로 표시하지 않는다.
- create/inspect/edit/accept/import 5개가 동일 경로 대상이다. import만 worker로 옮긴 것으로 무차단 완료를 선언하지 않는다. project의 동기 잔여는 별도다.

## 기존 경로 호환과 한계

invalid/oversize terminal의 기본 동작은 owner/pending 보존·close Busy이며 자동 취소/ACK/재실행은 없다. 명시 복구 receipt/아카이브는 미구현 잔여다.

기존 `TypedSdkPlugin`은 Immediate 반환·AlreadyTerminal cancel·동기 shutdown 계약을 그대로 유지한다. 기존 `ReviewHost`/`ReviewController`·RegistryProposalHost는 동기 소비자를 유지한다. 새 Pending adapter를 old host에 주입하는 것은 지원 완료로 간주하지 않는다. pending 소비는 명시 admission/result 경로로 연결하고 저장/accept의 성공 뒤 inspect도 다시 비동기 요청하여 같은 UI thread의 verifier를 피한다.

S1은 강한 in-flight 취소/rollback/publication reservation을 보장하지 않는다. S2와 실제 OS notifier→wake→Completion인 S3를 구별한다. headless typed terminal/수동 pump를 실제 OS wake나 전체 시각 검증으로 집계하지 않는다. [HP01~HP10 계획](../historical-import-pending-integration.md)의 구체 인수에 연결하며 gate 슬롯/공유 source freeze는 SDK·PM 배정을 따른다.

## codec 예산

AsyncCodecBudget은 max_pending/max_terminal_wire_bytes/max_total_codec_wire_bytes를 받는다. constructor는 pending×terminal-wire×4의 checked 예약이 총 예산 안인지 확인한다. 네 몫은 terminal 생성/registry 수락 임시값·accepted-event 보존·ACK 재시도/반환 복사에 대한 encoded-wire 예약이다. SDK canonical terminal 및 assembly typed Arc 캐시는 별도 예산이다. Core 개별 payload 1MiB 검증과 caller의 Completed payload/Failed(message+details) 전체 wire envelope를 모두 검사한다. borrowed 직렬화로 먼저 크기를 세어 큰 JSON Value/message 복사 전에 거부하고 생성 결과도 재측정한다. 초과는 원 terminal ACK0/close Busy다. 임의 사용자 Serialize/Deserialize의 내부 heap·DOM/object overhead까지 hard memory limit을 보장하지 않는다. count 제한만으로 bytes 예산이 구현됐다고 집계하지 않는다.

## 계약 조율 이력

초기의 K/AsyncTerminal 중간 제안은 메시지 교차로 철회했다. 최종 actual-ticket/Arc<Result>와 queued Requested 계약만 구현 기준이다. 기존 문서의 queued Completed 제안도 채택하지 않았다.

## 실제 문서 연결의 읽기 감사와 다음 최소 수직

초기 inspect는 아직 actual document scope가 없다는 조립 순환이 있다. SDK application의 plain ExecutionHandle은 Meari와 무관하므로 trusted launch 준비 단계에서 같은 owner로 submit/terminal을 다룰 수 있다. 이후 canonical snapshot으로 실제 root를 mount하고 동일 SDK owner를 actual scope의 Native5 parent에 연결한다. 최초 결과의 소유/ACK와 loading/cancel/close를 어디서 유지할지는 SDK launch assembly와 계약을 확정해야 한다. 이 단계를 동기 factory 호출이나 임시 scope로 우회하지 않는다. SDK가 API를 확정하기 전 새 launch port/receipt를 존재하는 API처럼 쓰지 않는다. 이것은 다음 수직 연결의 선행 미확정 항목이다.

후속 최종 계약은 위 선행 미확정 항목을 대체한다. 실제 SDK `InitialProposalInspection`과 document 전용 `ExecutionOwner`/단일 `ExecutionAttachment`를 사용한다. UI canonical typed·명시 source/revision/reference 검증→private immutable 준비 Arc 및 raw terminal 인수→initial ACK→actual ModuleProgram mount와 동일 owner의 Native5 attachment/register 순서다. initial ACK는 renderer/mount/사용자 품질 ACK가 아니다. ACK 실패 시 mount0/추가 submit0, 조립 실패는 같은 준비·owner로 조립만 재시도한다. 과거 full mount 뒤 initial ACK 제안은 quiescent attachment 조건과 순환이므로 폐기했다.

교정 원본은 현재 verification/proposal-review-intent.tsx, NeedsRepair는 studio/subtitles/document-repair.tsx 소비 시험에 있다. Card/HL factory는 교정 선택을 처리하지 않는다. 세 task 제품 비교/수정/명시 채택 최소 수직에는 교정 준비 책임을 공통화하고 기술 시험 전용 문구와 제품 표시를 구별하는 작업이 필요하다. 새 별도 테마나 동작을 만들지 않고 승인 디자인·공통 token/SVG/Pretendard를 적용한다. 이 source 연결 자체를 디자인 13화면 검증으로 집계하지 않는다.

### Completion·close의 소유 순서

1. 실제 callback/renderer guard에서는 기존 bounded intent admission만 수행한다. guard를 모두 해제한 뒤 queue를 drain하여 Pending submit을 한다. actual ticket과 ReviewSession token이 결합된 동안 입력·선택 전환을 막는다.
2. worker는 원 terminal을 보존하고 notifier만 호출한다. host Completion은 document guard 밖에서 pump를 호출한다. Core typed 수락 전 오류는 원 결과·pending 보존, 수락 후 SDK ACK 실패는 accepted-but-unacked를 보존해 ACK만 재시도한다. mutation은 다시 보내지 않는다.
3. save/accept receipt를 confirm_mutation으로 보존한 뒤 **별도 async inspect**를 한다. inspect 실패는 저장/채택 실패로 바꾸지 않고 명시 refresh를 제공한다. old source/scope/foreign ticket은 현재 문서에 적용하지 않는다. queued Cancelled는 사용자 취소로 표시하고 in-flight Completed/Failed의 실제 효과는 그대로 표시한다.
4. 새 props/bindings를 stage하고 실제 Native try_reproject/HostCommitReceipt가 성공한 뒤에만 projection-needed를 해제한다. 실패는 원 문서/export와 terminal 결과를 유지하고 새 mutation 없이 재투영을 재시도한다.
5. close 승인을 받은 뒤 새 callback/SDK admission을 막되 completion pump와 owner ledger는 남긴다. callback revocation과 queue discard는 즉시 할 수 있지만 terminal drain이 가능한 controller/registry를 먼저 버리지 않는다. cancel Requested/SDK ACK/worker join/parent shutdown이 끝나기 전 session_closed/parent_closed/HostCleanupComplete를 설정하지 않는다. 동시 close의 같은 checkpoint를 재사용한다.
6. close 중 이미 완료한 mutation은 실제 receipt로 보존한다. 새 inspect를 admission하지 못하면 refresh 필요/저장 revision을 보존하고 정상 문서에 적용 완료라고 표시하지 않는다. invalid terminal은 명시 복구 대기로 Busy, forced OS destroy/Drop은 ForcedIncomplete로 남긴다. SDK parent shutdown과 controller.close_sdk가 같은 registration을 이중 unregister하지 않도록 정리 권한은 하나로 조립한다.

### 필요한 소비 인수

### notifier 인계와 guard 해제 kick

1. loop owner/startup을 조립한 뒤 해당 wake를 얇은 infrastructure notifier에 넣고, 그 notifier로 기존 ExecutionOwner를 정확 한 번 시작한다. 실제 inspect가 loop 시작/문서 생성보다 빨라도 SDK retained terminal과 Native startup dirty가 각각 결과/알림을 보존한다.
2. 초기 ACK 후 원본 factory/bridge가 worker owner를 InitialExecutionParent로 이전한다. controller와 host에 새 ExecutionOwner를 각각 만들지 않는다. context.attach token→runner 인수 전후 실패는 같은 partial owner와 raw/typed snapshot을 회수한다. 반환 owner가 있는데 retry를 위해 신규 inspect/worker를 생성하지 않는다.
3. attached hook은 같은 runtime/wake를 notification/kick 목적으로 인수한다. startup wake가 이미 forwarding을 소유하므로 두 번째 target setter나 per-document thread를 추가하지 않는다. 실제 Ready/표시 관측과 구별한다.
4. callback admission에서는 queue만 수락한다. document/runtime/registry guard 밖에서 기존 drain→pump.accept→owner ACK→재투영 commit을 수행한다. 실제 guard 획득 실패만 typed transient OnWake로 남기고 guard 소유자가 해제한 뒤 해당 wake.wake()를 한 번 kick한다. 이미 수락한 callback·SDK mutation을 다시 enqueue하지 않는다.
5. genuine failure/예산 소진의 latch를 해제하는 retry_failed_completion 또는 request_close는 **명시 재시도** 경계다. 자동 guard-release kick으로 retry 예산을 매번 초기화하지 않는다. 메시지 문자열·모든 Busy code·redraw 반복으로 재시도를 분류하지 않는다.
6. guard 실패 출처가 현재 UI error 변환에서 소실되면 해당 UI-owned poll 경계에 typed guard 원인을 먼저 보존한다. SDK admission 전 실패와 이미 수락된 ticket의 terminal poll 실패를 구별한다. 전자는 사용자 intent/실패 표시를 보존하며 자동 Save 재실행 대상으로 삼지 않는다.

### typed close의 제품 매핑

| 실제 관측 | startup/부모 bridge의 다음 상태 | Native 재관측·보존 |
|---|---|---|
| WorkerExitPending { loop_finished } | 같은 worker owner/checkpoint 유지 | Pending + After(주입된 양수 지연). loop_finished는 join ACK가 아님 |
| TerminalAckPending | 기존 ticket/raw/typed 결과·명시 수용 경로 유지 | Pending + OnWake. timer 자동 ACK/강제 ledger 삭제0 |
| Closed(receipt) | worker_stopped/미ACK0의 실제 receipt 확인 후 해당 parent 단계 완료 | Complete, 해당 deadline 제거. 정상 child-first barrier 이후만 parent 최종 완료 |
| Faulted { kind, error:Arc, … } | 원 diagnostic Arc·retained_operations/peek·checkpoint 보존 | RetryableFailure/명시 복구. 종류 Terminal/WorkerJoin을 지우거나 join timer로 바꾸지 않음 |
| poll_close outer Err·registration unbind 실패 | 권한/poison/실제 adapter 오류 보존 | 일반 실패. Busy 문자열/NeedsInput code만으로 자동 retry0 |

join 관측 지연과 HostScheduleLimits(min/max/count)는 신뢰한 assembly/test 입력에서 함께 주입하고 매회 임의 기본값으로 넓히지 않는다. startup doc0 cleanup과 post-document runtime에 같은 범용 제한을 적용한다. canonical 초기 오류를 받은 경우 원 오류는 startup owner에 보존한 채 명시 수용/정리 checkpoint를 밟고, join 대기만 Pending(After)로 관측한다. 정리가 확인된 뒤 Stop/원 오류 반환을 구별한다. controller Err가 자동 cleanup을 수행하거나 Native Drop이 SDK ACK를 실행한다고 가정하지 않는다.

부분 mount 실패 회수는 기존 retry_unbind→동일 worker/prepared owner로 돌아가는 경로이며 위 final close와 다르다. 최종 poll_close를 시작한 owner를 다시 live 문서로 붙이지 않는다. ChildWindowHost profile은 child barrier 완료 뒤에만 제품 parent close/hint를 위임한다. 정상 close에서 child와 host join을 일부러 동시에 시작해 timer min을 시험하지 않는다.

### 제품 OS 연결 구현 배정 및 입력 인수 — 진행 중

PM이 후속 구현·단일 consumer 검증 슬롯을 배정했다. 위 WIP 제한은 당시 관측이며 현재 Native 최종 `2827a5a6b4b902ce00b4f1acbb1631b157c5c93dd41dea5ca50521753b63132a`의316파일과 기존 UI16의 실제 hash 대조는 차이0이다. UI16 before 사본과 관측값은 `runtime/quality-review/ui-native-pending-r1/`에 보존했다. SDK 조립5파일 최종 `9CA03C7A223B7CF5332FE4CAEBEB035BD36F8E00CDB8A8A32BC6CC7668B6579C`를 인수했다. consumer window feature/lock은 SDK 담당이 offline resolution으로 확정했으며 제품 UI가 임의 수정하지 않았다.

현재 작성한 `window_startup.rs`는 기존 InitialPanelStartup의 prepare→ACK→같은 handoff/mount→bridge→strict runtime→context.attach_observed 순서를 소비한다. Native의 최종 plain observer는 실제 Ready와 FrameSubmitted의 render-time HostStamp를 제공한다. attached hook 성공을 화면 생성으로 세지 않는다. InitialExecutionParent는 typed close 원 관측 전체와 Fault Arc를 유지하고, parent port는 기존 Immediate lease에 source-compatible Complete default를 둔다. worker-exit만 주입된 양수 delay를 사용하며 terminal ACK 대기와 genuine fault를 timer 자동 ACK/자동 복구로 전환하지 않는다.

기존 실제3task fixture·원본 ModuleProgram inventory·semantic assertion을 support/pending_document_case.rs로 추출하고, 원래 headless83 의미를 유지하는 회귀와 신규 native_pending_window_sdk.rs를 작성 중이다. 신규 OS 시험은 normalized callback 입력이며 물리 키보드·IME·시각13화면 검증이 아니다. completion registry borrow 실패의 출처는 pending host→controller→document→bridge로 별도 보존하며 provider/admission Busy 전체를 자동 transient로 취급하지 않는다. 실제 guard-release kick·commit 실패·doc0·partial recovery와 SDK bundle failure/notifier 오류의 인수 근거는 추가 시험이 필요하다.

첫 `--offline --locked -j1 --no-run`은 중앙 runner/기존 consumer target/affinity3/BelowNormal/RUST_TEST_THREADS1에서 진행 중이다. 이 절은 구현 후보 및 입력 인수 기록이며 컴파일·기존83·strict/fmt·실제OS 통과 기록이 아니다. root presentation 등록/main/eframe 변경과 전체 시각 완료는 포함하지 않는다.

### 제품 OS 소비 gate 최종 인수

위 진행 중 문구는 당시 이력이다. [최종 검증 정본](../../../sots/verification/presentation/native-pending-window-sdk-2026-10-20.md)에 최초 실패·수리·최종 입력을 구분했다. 최종 UI19 inventory SHA256 `26335921b555b8732b3609f9d22a7ad7dda93b9f5e3d4998111381818774f35c`, full-final82040ms/exit0·91pass/0fail/9ignored, 같은 source의 strict-commit-r2/fmt-final exit0, 별도 실제OS9개 각각exact1pass, 최종owned[]다. 원83 의미를 유지하며 추가 guard 회귀1과 새 target에 중복 포함된 initial7을 독립 신규 성과로 합산하지 않는다.

실제 Native Ready/checked submission, SDK3task 의미·worker-thread 처리, initial ACK 전 mount 금지, doc0 정상/오류의 최종 notifier barrier와 타이머 join, 늦은 notifier 진단, registry guard 해제 wake1, 같은 prepared/worker의 부분 mount 복구, trusted apply의 commit 전 거절·projection 보존·명시 retry receipt를 인수했다. join/ACK 내부 호출 계수와 OS compositor ACK·물리 입력·시각13화면은 별도 범위다. trusted commit port는 기본 Native 위임의 construction-time UI 경계이며 외부 입력·global setter를 제공하지 않는다.

소비 gate를 마치고 heavy 슬롯을 PM에 반환한다. 필수 다음 단계는 SDK/UI 소유를 나눈 root optional feature·canonical presentation façade·명시 launch DTO·같은 client/owner의 실제 player.exe 조립 및 실행 검증이다. 현재 root 등록/main/eframe은 변경하지 않았고 전체 제품 목표는 미완료다.

실행은 Native 최종 API/pin·PM 파일 소유/manifest/단일 슬롯 인수 후에만 한다. 먼저 같은 consumer의 집중/기존83·strict/fmt, 그다음 지정 실제 OS3task/문서0 종료 gate·소유 window/process/worker 정리와 입력 불변을 별도로 기록한다. 실제 video/browser child·제품 런처·전체13화면/모든 탭·시각/키보드/a11y 범위는 유지하며 이 계획이나 부분 OS gate로 완료를 대체하지 않는다.
