## 재사용할 실제 경로

`product_window/mod.rs`는 기존 ExecutionOwner를 받아 InitialPanelStartup→canonical inspect→document_factory→PendingReviewController를 조립한다. register_output_reviews와 factory의 capability 검사/enable_output_reviews도 실제 연결되어 있다. panel_model/correction_panel은 같은 NodeLease/FIFO에 output_review_panel의 콜백을 등록한다. 초기 unavailable 문구만 보고 미구현으로 판단하지 않는다.

Card 하나를 첫 제품 연결 단위로 한다. 명시적 proposal ID와 item index를 받아 기존 proposals.inspect의 StoredProposal에서 draft revision 및 source ID/revision/SHA를 보존한다. 기존 bootstrap의 전체 identity/target 검사를 그대로 통과시킨다. source/generated raw/draft/accepted 비교, 사람 편집, save, 명시 accept, inspect 재열기와 출력 판정은 기존 controller/session/typed API를 소비한다. 수락과 출력 품질 판정은 다른 사용자 동작이다. 선택이 없으면 입력을 요구하며 index0을 자동 선택하지 않는다.

현재 main의 기본 경로는 eframe이며 NativeViewer 후보도 view.start만 준비한다. routing catalog는 런타임 등록 증거가 아니다. product_native_launch.run을 route callback에서 다시 부르면 SDK 실행/Native loop 소유권을 중복 생성하므로 사용하지 않는다. launch JSON 파일이나 CLI/새 프로세스를 제품 내부 전환 매개로 사용하지 않는다.

## 실제 막힌 경계와 구현 순서

1. ViewerCallbacks는 현재 원 SDK 실행의 exclusive attachment를 소유한다. proposal adapter도 attach하므로 동시에 등록하면 Busy다. 기존 prepare_release는 endpoint worker join 이후 전체 종료용 계약이다. 이를 route 전환에서 그대로 호출하지 않고 **원 scope를 확인하는 scope-only release 진입점**을 추가한다. 내부 invalidate→begin_close/cancel→원 ticket 보존→terminal ACK→unregister→quiescent attachment release는 공유한다. endpoint/ExecutionOwner를 닫지 않는다.
2. 전환 중 이전 콜백을 거부하고 ticket이 남으면 같은 원 owner/receipt를 유지한다. `None` 이후에만 기존 proposal adapter가 같은 execution에 attach한다. 실패/Busy에서 새 worker나 새 ID로 우회하지 않는다. 이후 전체 종료는 활성 route의 등록과 ticket까지 정리한 뒤 원 ExecutionOwner를 닫도록 연결해야 한다.
3. Card 경로는 기존 bootstrap/module inventory/document_factory를 이용한다. 전체 InteractiveDocument를 임의 대입해 stamp/slot/source scope 검사를 우회하지 않는다. 기존 ModuleProgram node slots 또는 검증된 scoped remount 계약을 사용한다. 현재 graph는 module당 component 하나인 제약이 있으므로 여러 export를 추측하지 않는다. 필요한 최소 재현만 Meari에 요청한다.
4. selection callback→canonical inspect→준비한 panel→원 프레임 outlet→save/accept→재열기를 연결한다. 기존 NavigationGuards의 dirty/pending/recoveryBlocked를 보존한다. 이 단계는 아직 구현/실행 완료가 아니다.
