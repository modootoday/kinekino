후속 공식 웹 조사에서 고정 HF e71 revision 자체의 LICENSE 추가 diff와 Silero Team MIT 본문을 확인했다. 아래 license 행의 ‘본문 bytes/pin 미인수’는 유지되지만 공식 본문 위치를 모르는 상태는 해소됐다. ## PM이 고를 다음 정확 delta와 실행 전제

이미 확보한 weights·WAV2를 다시 다운로드할 필요는 없다. 다음 record delta의 책임 경로는 기존 `src/application/audio_vad/product_release.rs`의 ProductReleasePins/NativePins이며 weights/revision은 현재 cached_silero에 고정돼 있다. 그러나 **license 본문 pin·native 전용 worker pin·실제 full manifest pin·dependency/notices·최소 OS 승인값이 부족하므로 지금 None을 바꾸는 delta는 만들지 않는다.** README59B, 다목적09F BIN, default6AF BIN, synthetic child22 pin을 빈자리에 넣지 않는다.

PM은 (1) 배포 담당이 위 누락 파일/원 출처·pins를 공급하고 독립 선택을 인수한 뒤 최소 record delta를 배정하거나, (2) 기존 실제 weights/WAV2와 현재 고정 native build 입력으로 **생산 등록과 분리된 전용 worker 기술 build/load/ABI gate**를 명시 배정할 수 있다. 후자도 기존 loader/notice/원 owner 검사를 우회하거나 fixture로 권한을 자기승인하지 않으며 필요한 정확 native 입력을 먼저 공급해야 한다. 과거 실험 허용은 새 실행 슬롯 배정이나 제품 배포 허가를 자동 제공하지 않는다.

두 경우 모두 추가 worker 빌드·추론·다운로드는 PM의 새 명시 범위/자원 배정 후다. cacheunknown2/all protected=false는 계속 남고 공유 캐시를 안전 재사용으로 표시하지 않는다. 현재 source-only 후보 단계에서는 신규 engine/tool 실행·Cargo·OS probe·record 수정·미디어 복사0이다. 새로운 기술 gate에서는 정상 CLI test=false BIN과 입력2 binding을 별도 Rust consumer로 동결하고 실제 submit/watch/get·원 source/output·취소/재시도/nooverwrite/owner/EOF를 검증해야 한다. 사용자 모델 품질 검토는 제품 연결 후 별도 마지막 단계다.
