# 카드 묶음의 Jobs 실행과 디렉터리 발행

R109 정정: 원 Jobs의 begin_verification은 발행 후 상태 전환이다. R108 첫 실제 실행은 이 호출을 staging 검사 전에 잘못 사용해 NeedsInput/"Verification requires publication"으로 끝났고 원 worker는 정상 종료했다. 원 Jobs 상태 계약은 바꾸지 않았다. R109는 staging 자체 검증→원 reserve_publication→원 handle rename→begin_verification→발행 후 확인 순서로 연결했다. 원 실패/부분 staging/preimage는 보존한다.

2026-10-28 R108 구현 계약. [실제 파일/자산 adapter](card-bundle-file-adapter.md)와 [준비 계약](card-bundle-preparation.md)을 기존 media-jobs JobExecutor/PreparedJobInput/SourceBlobStore/ExecutionControl에 연결한다. 현재는 명시 Rust composition에서 등록 가능한 CardBundleJobExecutor이며 기본/CLI host에는 아직 등록하지 않았다. production.export_cards의 직접 SDK/CLI 지원을 주장하지 않는다.

prepare는 strict CardBundleRequest·기존 parameter byte 한도를 검사하고 원 CardProjectStore에서 선택한 불변 발행과 실제 PNG/template/font를 고정한다. PreparedCardBundle을 기존 UTF8 source blob에 보존한다. source blob SHA는 준비 descriptor의 SHA이며 원미디어 bytes hash나 cue source hash가 아니다. expected_source_sha256도 이 descriptor를 의미한다. execute는 원 blob hash/bytes와 저장 pin·현재 입력 관측을 다시 대조하며 최신 프로젝트로 자동 갱신하지 않는다. 실행 예산 상한은120초, 기본 준비 값은30초다.

execute_bundle은 원 Jobs ExecutionControl의 JobAttemptIdentityV1을 요구한다. 임의 JSON/요청 ID/새 worker로 원 attempt를 대체하지 않는다. attempt.json은 원 worker가 제공한 job/attempt/input/source blob provenance를 기록하며 권한/cleanup/품질 증명이 아니다. 실행 중 카드 사이·IO 단계 경계에서 원 취소/deadline을 확인한다. 한 카드의 동기 CPU raster를 강제로 선점하는 wall deadline/취소를 제공한다고 표시하지 않는다.

## 산출물

- 원 frame hash별 PNG와 artifact→상대파일/크기/hash 매핑
- 순번/역할 카드 PNG 및 카드별 provenance JSON
- caption.txt, alt-text.json, 편집 가능한 CardPublication의 project.json
- 모든 산출물의 이름/hash/bytes/media type, 저장 발행/편집 revision·템플릿/공통 자산 pin·원 attempt·review_artifact/quality_approved=false를 기록한 manifest.json

프로젝트의 원 frame 참조를 복원할 수 있도록 raw frame도 묶음에 넣는다. 원 media/PTS·권리·모델 품질을 새로 인증하지 않는다. 폰트는 제품 공통 자산 계약의 hash/license 참조와 기존 per-card provenance를 보존하며 OS 폰트 설치/다운로드가 아니다. manifest 자신은 자기 hash 목록에 넣지 않고 최종 VerifiedJobOutput의 path/SHA/bytes로 별도 식별한다.

## 발행 경계

새 출력 parent의 기존 fixed-root/ancestor guard를 유지하고 같은 parent에 GUID 이름의 private staging 디렉터리를 만든다. 원 directory handle은 READ/DELETE 접근과 경쟁 rename/delete 거절 상태로 유지한다. 각 파일은 create_new·write_all·sync_all 후 실제 handle/FileID·size/SHA로 검증한다. 한 파일은 공통 PNG byte 한도, 전체 묶음은512MiB로 제한한다. 이름은 프로그램이 생성한 portable 단일 component만 사용한다.

모든 파일을 staging 원 handle에서 재검증한 뒤 원 control.reserve_publication의 durable gate를 사용한다. child writer는 닫되 원 directory handle은 유지한 채 FILE_RENAME_INFO의 ReplaceIfExists=false로 한 번에 이동한다. 이미 있는 파일/디렉터리를 지우거나 교체하지 않는다. 이동 후 begin_verification으로 원 Jobs 상태를 전환하고 원 directory FileID와 각 파일 FileID/bytes/hash를 대조한 뒤에만 VerifiedJobOutput을 반환한다. 기존 다운로드 adapter의 handle rename 패턴을 참고하되 원 다운로드 소유 코드는 수정하지 않았다.

API 근거: [Microsoft FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info)의 ReplaceIfExists=false는 대상이 있으면 오류를 반환한다. [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle)와 [directory handle](https://learn.microsoft.com/en-us/windows/win32/fileio/obtaining-a-handle-to-a-directory)의 handle 기반 계약을 따른다. 이 문서만으로 새 호스트의 race/crash 인수를 통과한 것으로 계산하지 않는다.

## 실패와 미완료

실패/취소된 private staging을 자동 삭제/재사용하지 않는다. 원 attempt 파일과 부분 산출물을 보존하고 partial_cleanup_supported=false를 기록한다. Cancelled는 원 작업의 취소/worker 종료이며 물리적 부분 파일 삭제 성공이 아니다. generic Jobs의 취소 ACK가 failure details를 별도 보존하지 않는 경우에도 staging의 attempt.json으로 원 job/attempt를 식별한다. 자동 부분 성공 재사용/실패 카드만 retry는 아직 구현하지 않았다.

rename 이후 최종 검증/Jobs 결과 저장이 실패하면 이미 존재하는 출력은 보존하며 Completed로 바꾸지 않는다. 발행 후 ACK 복구/재조정·강제 crash/power-loss·disk-full/permission fault·디렉터리 할당 직후 실패의 완전한 복구 metadata는 후속 공백이다. 출력 디렉터리가 존재하는 재시도는 충돌로 거절하며 기존 결과를 자동 성공으로 채택하지 않는다.
